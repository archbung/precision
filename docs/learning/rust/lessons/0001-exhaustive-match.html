LESSON 0001 · 30 MINUTES · PREDICT, COMPILE, EXPLAIN

One decision for every variant

Your maintenance skill today: explain how Rust makes you handle every measurement mode. Start with the enum and as_str in src/exercise_types.rs. Precision's exercise identity decision gives this a familiar domain meaning.

Your Haskell background gives us a bridge: read this as a case analysis over alternatives, then test exactly what Rust checks. Spend about 5 minutes reading, 5 predicting, 15 experimenting, and 5 explaining.

Read just this part

pub enum Measurement {
    Repetitions,
    Duration,
    Distance,
}
// Inside impl Measurement:
match self {
    Self::Repetitions => "repetitions",
    Self::Duration => "duration",
    Self::Distance => "distance",
}

A measurement value is one of these alternatives. Here Self means Measurement. Each arm pairs a pattern with the expression after =>; the matched expression becomes the match's value. Rust requires all possibilities to be covered. Sources: enums and match.

For this lesson, treat the surrounding function signature as “returns text.” We will unpack self, &'static str, traits, and Result individually later.

Predict before running

  1. What text does Measurement::Duration.as_str() return? Point to the arm that determines it.
  2. If you remove only the Distance arm while keeping all three variants, does compilation succeed? Explain why.
  3. Would the compiler reject changing the Duration arm's output to "distance"? What does that tell you about the boundary between compiler checks and behavior tests?

Your compiler experiment

After predicting, save a scratch copy of only the enum and its impl Measurement under this learning workspace (omit serde attributes and imports; add an empty fn main() {}). Remove one arm yourself. Compile it with rustc --emit=metadata --out-dir /tmp scratch.rs from the scratch file's directory. Report the diagnostic, restore the arm, and explain the difference. Do not change the production enum or add a new domain measurement.

If making that scratch copy is unfamiliar, ask for help with the setup; the actual edit remains yours. The teacher has not implemented this exercise.

Transfer the idea

In your scratch copy, try a second version with a wildcard arm instead of one explicit variant arm. Predict what happens if you then add a hypothetical fourth variant to the scratch enum. Compile both versions and explain which one forces you to revisit the mapping. This is an isolated language experiment, not a proposed domain change. Then explain how the same reasoning applies to the existing LoadConvention::as_str.

Keep the evidence precise

The enum reflects an existing domain design choice. Exhaustiveness is a language correctness check. Whether a string is the right representation needs a behavioral check. We have made no claim about the module's overall style or performance.
